## 1. Purpose and evidence rules

This is the durable retrospective for the EdgeHub 1.0 project. It records:

- what was built and changed;
- what defects and risks were found;
- what was fixed;
- what testing methods proved useful;
- what testing methods produced false confidence or wasted time;
- what worked well with agents and reviewers;
- what did not work well with agents and reviewers;
- which findings are still open, waived, or not tested;
- a reusable operating model for future projects.

This document summarizes a large body of detailed source material. It does not
replace the individual widget specifications, hardware logs, audit reports, or
release receipts. The final section links those canonical records.

The following evidence rules apply throughout:

1. A pass belongs to the exact source and binary that was tested.
2. A dirty-tree result is an observation, not release evidence.
3. `not tested`, `tested and failed`, `cancelled`, `waived`, and `passed` are
   different states.
4. A green test is trustworthy only if a deliberate violation has proved that
   the test can turn red.
5. A checklist count is not automatically a coverage percentage.
6. Automated personas and LLM role-play are useful review lenses, but they are
   not real user research or professional certification.
7. Agent reports are inputs to verification, not authority by themselves.
8. The code, exact test output, signed artifact, and public download take
   precedence over stale planning prose.

## 2. Executive summary

EdgeHub 1.0 shipped as a signed stable release with:

- a native Linux Hub and separate Manager;
- 30 first-party widgets;
- 19 preset screens;
- portrait and landscape display support;
- live Manager-to-Hub control and Hub-to-Manager reflection;
- Standard and Immersive Hub control modes;
- real preset previews using the actual packed widgets;
- responsive widget layouts and shared readability rules;
- improved history charts with axes, raw peaks, smoothing, and selectable
  line or bar presentation;
- AppImage, Ubuntu 26.04 DEB, and Fedora 43 RPM downloads;
- signed checksums and an official AppImageUpdate RC-to-stable round trip;
- a real-behavior marketing film, theme and accent showcase, stills, captions,
  and an original sample-free soundtrack.

From `v1.0.0-beta.1` to stable, the repository recorded 135 non-merge commits:

| `test` | 69 |
| `fix` | 48 |
| `docs` | 8 |
| `feat` | 4 |

That range changed 521 files. The large insertion count includes generated

hand-written product-code volume.

The strongest general lesson is:

> Test integrity mattered more than test quantity. Several of the most serious
> defects survived behind green checks that never executed, matched zero
> subjects, tested an old binary, or averaged away a failing component.

The largest process failure was excessive repetition of broad, expensive test
runs after the user had already asked for the single failing case. This wasted
time, tokens, and GitHub Actions minutes. Future work must use focused
failure-first iteration and reserve full suites for defined integration
milestones.

## 3. Project outcome by phase

### 3.1 Foundation and architecture

The final implementation uses:

- Rust for configuration, metrics, display logic, policy, licensing, secrets,
  and the C ABI;
- C++17 and Qt 6 for process bootstrap, display integration, IPC, MPRIS,
  notifications, Manager backend, and QML bridging;
- QML for the Hub, Manager, dashboard store, shared controls, widgets, previews,
  presets, themes, and settings;
- a hand-written C FFI, not `cxx-qt`;
- a shared `DashboardStore` and a shared `WidgetHost`;
- one per-user local control socket resolved through one common path helper;
- compiled Qt resources for shipped QML, fonts, icons, wallpapers, and Manager
  assets.

Architectural lessons:

- The architecture document must describe the code that exists. Earlier prose
  mentioned `cxx-qt`, while the product used a hand-written C ABI.
- FFI ownership rules need to be explicit. Returned strings use the
  `XeneonString` RAII wrapper and opaque handles have matching free functions.
- QML resource aliases are part of the runtime API. A file that is not added to
  `ui/qml.qrc` does not exist to the shipped application.
- A generator that once created files is not necessarily the current source of
  truth. `scripts/gen_widgets.py` became dangerous after the widgets were
  hand-developed. It once replaced a real widget with a small stub. The safe
  rule is now to hand-edit widgets and never force-regenerate them.
- Shared lifecycle and state contracts reduced duplicated fixes. `WidgetHost`,
  `ProviderState`, shared config controls, common charting, and catalog metadata
  were more effective than 30 unrelated local patches.

### 3.2 Data safety and configuration

Implemented:

- configuration stored at
  `$XDG_CONFIG_HOME/xeneon-edge-hub/config.toml`;
- application config directory checked as a real, owner-matched directory and
  forced to mode `0700`;
- config, lock, backup, and temporary files use mode `0600`;
- writes use a sibling temporary file, complete write, file `fsync`, atomic
  rename, and parent-directory `fsync`;
- cross-process transaction locking and compare-and-swap style stale-save
  protection;
- schema checks, size limits, ownership checks, symlink refusal, and corrupt
  config recovery;
- clean shutdown flushes widget-local buffers, then the shared store;
- connected Manager saves go through the Hub, preserving the single-writer
  model;
- screen deletion is confirmed and the final screen remains protected;
- configuration reset and personal-data erase are separate actions;
- local installs back up the live configuration before package replacement.

Important limits:

- HTTP tokens, KPI tokens, private calendar URLs, widget content, and the
  licence key may still exist as plaintext in `config.toml`.
- Environment and file references avoid storing resolved secrets, but a
  Secret Service backed credential store is not implemented.
- Atomic persistence protects completed writes. It does not prove that data
  typed less than the debounce interval before SIGKILL or power loss is saved.
- The Hub and Manager share one process-level QML engine per application.
  Widget loader and JavaScript handler failures are locally contained, but a
  fatal native or engine failure can still terminate the Hub.

### 3.3 Hub, Manager, and live integration

Implemented and fixed:

- Manager can add, remove, resize, reorder, rename, and switch screens;
- Manager can change theme, accent, background, wallpaper, typography,
  display settings, startup settings, and relevant widget configuration;
- Hub and Manager use the same stored appearance instead of partially applying
  theme or accent fragments;
- Manager previews reserve the same Hub control-bar geometry;
- Manager previews render the actual widgets and actual packed layout;
- preview orientation follows the active Hub orientation;
- previews are passive and cannot create duplicate timers or network polling;
- live Hub state is reflected back into Manager;
- typed page names are saved instead of silently disappearing on focus changes;
- preset selection is review-first, with purpose, audience, setup
  requirements, and layout visible before adding;
- the Manager is never started by Hub startup or by package installation;
- Manager startup refuses an Edge-only display set;
- on KDE Wayland, Manager uses XWayland when no explicit platform is selected,
  allowing enforceable placement on a desktop monitor;
- a runtime guard hides and exits if the compositor still maps Manager on the
  Edge.

Key lessons:

- WYSIWYG requires shared geometry and shared state, not a visually similar
  mock.
- A preview must not become a second active runtime driver.
- Wayland does not offer portable top-level placement guarantees. Platform
  policy must acknowledge compositor reality rather than trust `setScreen()`.
- The safe fallback for "Manager might open on the Edge" is to refuse startup,
  not to show it and hope.

### 3.4 Display targeting and orientation

Implemented and fixed:

- target display matching and missing-target behavior;
- persisted fallback orientation;
- bounded startup HID acquisition retries;
- software orientation control and automatic orientation reflection;
- smooth Hub rotation transitions;
- immediate Manager preview reflow while the physical Hub transition animates;
- restart, scaling, primary-role change, disable, reconnect, and exact layout
  restoration tests;
- mixed-DPI screenshot crop scaling;
- protection against placing the Hub on the primary desktop when the configured
  target is missing.

Important findings:

- The initial HID acquisition used too few attempts and a persisted value could
  suppress its delayed retry. This was a product defect, not merely missing
  evidence.
- The first smoothness fix regressed into harsh immediate rotation. Temporal
  behavior needs a direct animation test and a visual review.
- Real display screenshots may be in framebuffer coordinates while KScreen
  reports logical coordinates. Cropping without scale conversion creates false
  failures.
- Synthetic touch must prove device mapping, transform, and landing before any
  action. Refusing uncertain injection is correct.

### 3.5 Standard and Immersive controls

Implemented:

- versioned `hubControlsMode: standard | immersive`;
- Standard as the safe default;
- Immersive removes the Hub bottom bar;
- per-widget configuration remains accessible on the Hub;
- Manager can restore Standard mode;
- an active Hub edit is allowed to finish before the bar disappears;
- Manager preview geometry follows the selected mode;
- empty-state copy explains that Manager is required in Immersive mode.

Lesson:

- A mode that removes its own recovery controls needs an explicit recovery
  route and safe transition behavior. It must not trap the user in edit mode.

### 3.6 Accessibility and readability

Implemented:

- Comfortable Hub text default at 1.15 scale;
- shared minimum text-size tokens;
- larger Manager typography and control sizes;
- 48 logical-pixel minimum interaction targets;
- accessible names, roles, keyboard activation, and focus rings for shared
  controls;
- contrast-safe text and accent derivation;
- reduced-motion behavior that removes flashes and scaling instead of merely
  changing easing;
- numeric contrast and minimum-type-size scans;
- golden-image visual baselines and diff review;
- fixes for ancestor clipping, constrained font metrics, wrapped text, button
  overflow, and unsupported dense sizes;
- compact layouts hide secondary information before shrinking primary content
  below the legibility floor.

Lessons:

- Font family availability changes layout. A test environment with one generous
  monospaced font can hide overflow that appears with a fallback font.
- `Layout.maximumWidth` alone may not constrain an implicit width. A preferred
  width, wrapping, or elision policy must also participate.
- "No clipping" cannot be proved from schema acceptance. The real rendered
  glyph geometry must be measured.
- Low contrast and excessive density were systemic token problems first. It was
  more effective to fix the shared design system and then create widget-specific
  tickets only for residual failures.

### 3.7 History charts and graphs

The original sparkline was a normalized decorative trace. User feedback
correctly identified that it did not explain whether a shape was a real spike,
what the values meant, or how much time was represented.

Implemented:

- fixed or automatic truthful value domains;
- an option to include zero so tiny changes do not appear as huge spikes;
- readable value labels on the vertical axis;
- a real retained-time span on the horizontal axis;
- minimum, average, current, and peak statistics where space allows;
- explicit raw peak marker;
- smooth mode using an emphasized exponential trend while retaining the raw
  trace;
- line mode for exact samples;
- bar mode for countable individual samples;
- comparison series support;
- value, unit, precision, label, and interval configuration;
- accessible text summaries;
- transition logic that moves between history snapshots rather than jumping;
- protection against curve overshoot inventing a spike;
- in-place array mutation detection so the chart repaints when a producer
  pushes into an existing history object.

Lessons:

- Never smooth away the raw truth. Smoothing is presentation, not data
  replacement.
- A graph without units, time range, scale policy, and accessible summary is
  decoration, not a statistics view.
- Automatic scaling must disclose whether zero is included.
- Animation tests must assert the intermediate state, not only the final
  endpoint.

  landscape marketing assumption.

  requirements must all describe the same user outcome.

### 3.9 Notifications and reminders

Implemented and fixed:

- persistent, more prominent in-app reminder presentation;
- clear Break and Focus due states;
- reduced-motion-safe alert behavior;
- snooze and schedule awareness;
- desktop notification bridge tests and real desktop integration evidence;
- notification availability and fallback paths covered without presenting a
  short transient flash as sufficient.

Lesson:

- A reminder is not useful merely because it technically appeared. It must be
  visually distinct, persist long enough to act on, and remain safe for users
  who reduce motion.

### 3.10 Security, privacy, and egress

Implemented and verified:

- Rust core has no network stack;
- network widgets go through a shared `NetHub` policy boundary;
- network namespace containment;
- exact hosted no-egress attestation with DNS/TCP sink, syscall observation,
  liveness, and negative controls;
- request timeout and response-size controls;
- HTTP/1.1 transport policy to avoid a recurrent Qt HTTP/2 cleanup warning;
- masked secrets in UI;
- reference-based secret resolution;
- local KPI file canonicalization, root policy, symlink refusal, regular-file
  check, and 1 MiB limit;
- remote artwork refusal;
- local wallpaper URL allowlist;
- release supply-chain workflows, dependency checks, CodeQL, notices, and
  signed artifacts;
- GitHub private vulnerability reporting instead of an unregistered email
  domain.

Important distinctions:

- A route-less network namespace proves containment.
- It does not alone prove that a connection was never attempted.
- The combined hosted test is authoritative for the stronger observation-window
  claim.
- Same-UID processes can drive the local control socket. File-system
  permissions exclude other Unix users but are not an authentication boundary
  against malware in the same session.
- Config secrets are protected by permissions, not encryption.

### 3.11 Licensing

Implemented:

- offline Ed25519 licence verification;
- Free retains all functional features, widgets, presets, layouts, and Manager
  capabilities;
- Pro is limited to optional cosmetic themes;
- Manager activation checks keys offline and pushes entitlement through the
  Hub single-writer path;
- issuer tooling is separate and is not shipped with the application;
- release certification licence minted without exposing the private seed.

Operational lessons:

- Private seed files must contain the actual issuer seed and use mode `0600`.
- The issuer directory should be private.
- Never place the seed value in a command line, environment log, artifact, or
  chat.
- A successful licence file should be non-empty, mode `0600`, and match the
  expected structured key syntax.
- Licensing should fail soft for ordinary product use and fail closed only for
  the gated cosmetic entitlement.

### 3.12 Packaging, updates, and release delivery

Implemented and fixed:

- exact version identity derived from Git tags;
- AppStream prerelease versions use sortable `~rc.N` syntax;
- local Arch package build and guarded `update-local.sh`;
- clean AppImage, Ubuntu DEB, and Fedora RPM builds;
- install, launch, metadata, identity, autostart, and removal lifecycles;
- AppImage dispatch can start Hub by default or Manager only on explicit
  request;
- AppImage autostart stores a persistent invocation rather than an ephemeral
  `/tmp/.mount_*` path;
- package installation never starts Manager;
- stable public checksums and detached signature;
- official AppImageUpdate from public RC to public stable;
- fresh public download verification;
- release repository renamed to
  `skyphoenix-it/skyphoenix-edgehub-linux`;
- public text avoids representing the project as affiliated with Corsair.

Release incidents and lessons:

- Local package versions originally sorted below the installed prerelease,
  making a new build look like a downgrade and allowing a package manager to
  revert it.
- CI checkout depth originally omitted tags, degrading AppImage version identity
  to an unorderable SHA.
- DEB and RPM metadata could disagree with binary identity until all packaging
  paths used the exact release version.
- Fedora minimal containers apply `tsflags=nodocs`. The stable RPM contained its
  documentation, but the clean lifecycle container discarded it. Inspecting
  the RPM payload proved the package was correct; clearing the container flag
  fixed the test.
- The old standalone zsync 0.6.5 client refuses GitHub's redirected target URL.
  The supported `gh-releases-zsync` path uses AppImageUpdate's GitHub Releases
  implementation and passed, reusing 99.025761 percent of the RC and fetching
  1,150,976 bytes.
- AppImageUpdate warned that the AppImage itself is not internally signed. The
  download is protected by the signed release checksum manifest, but internal
  AppImage signing remains a possible future hardening item.
- The GitHub release is not marked immutable by repository policy. The signed
  tag and signed checksums protect identity, but immutable-release settings
  should be evaluated for future releases.

## 5. Testing findings and reusable lessons

### 5.1 What worked

- Separate Rust and C++ coverage gates prevented one large codebase from hiding
  a weak smaller component.
- Resource-aware QML tests exercised compiled assets rather than accepting
  thousands of missing-resource warnings.
- Catalog-derived matrices prevented new widgets and sizes from silently
  escaping coverage.
- Visual baselines turned an impossible manual screenshot inventory into
  reviewable diffs.
- Negative controls proved security, network, link, package, and test-discovery
  gates could fail.
- Real-binary runtime tests caught lifecycle and lock behavior that unit tests
  could not.
- Real hardware testing found display, scaling, input, compositor, and process
  issues that offscreen QML could not show.
- Exact package lifecycle tests found metadata, docs-installation, autostart,
  dispatcher, and uninstall problems.
- Commit-keyed evidence and signed manifests made release claims reproducible.
- Fail-closed input automation prevented unverified touches on the user's
  desktop.

### 5.2 Green checks that were not trustworthy

The project found several forms of vacuous success:

| Failure shape | Example | Corrective rule |
|---|---|---|
| Test never registered | QtTest `test_x_data()` existed without `test_x()` | Lint live test names and prove the case can fail |
| Gate matched zero subjects | Empty QML requirement input or empty docs tree passed | Count subjects, print the count, make zero fatal |
| Parser failure skipped the gate | C++ coverage parsed as `n/a` | Fail on missing metric before applying threshold |
| Old binary under test | QML changed but `qrc` binary was not rebuilt | Rebuild before sabotage or runtime E2E |
| Property asserted instead of pixels | A value existed but rendered text still clipped | Assert observable geometry and screenshots |
| Aggregate hid a failure | Combined Rust+C++ percentage looked healthy | Enforce each language separately |
| Allowlist hid warning drift | Thousands of resource warnings were treated as normal | Test compiled resources and fail on unexpected warnings |
| Final command masked failure | Ad hoc zsync command ended with an unconditional PASS echo | Use strict shell mode and assert every intermediate result |

### 5.3 Coverage reporting

Correct language:

- Rust line coverage passed its enforced 95 percent gate.
- C++ line coverage passed its independently enforced 95 percent gate.
- The combined percentage is diagnostic only.
- The QML report means 100 percent of the currently enumerated requirements
  have assertion-backed claims.

Incorrect language:

- "Combined coverage proves the C++ gate."
- "QML behavior coverage is 100 percent" without defining and governing the
  denominator.
- "No issue reproduced" without naming the test capable of reproducing it.

### 5.4 Hardware and compositor lessons

- One shared physical desktop needs one test lease. Concurrent agents and owner
  interaction contaminated otherwise valid evidence.
- Synthetic input needs exact process, window, output, transform, landing, and
  owner-idle proof.
- A noisy Logitech G502 generated compositor activity and repeatedly tripped the
  safety gate. Isolating the exact device during approved runs worked, with
  keyboard and touchscreen still available as abort sources.
- Always restore display and input state in a `finally` or trap path.
- Spectacle output can use framebuffer rather than logical coordinates.
- Qt Quick selected unusable Zink on the hosted runner. Explicit LLVMpipe plus
  bounded renderer threads retained real rendered-pixel testing.
- Headless renderer oversubscription turned a short failure into a 45-minute
  cascade. Concurrency must reflect per-process renderer thread pools.
- Offscreen and software scenegraphs can differ from physical GPU output.
  Capture tooling must say which path produced the evidence.

### 5.5 Time and locale lessons

- Tests around midnight must not assume that `HH:mm` alone identifies "ten
  minutes ago."
- DST, overnight schedules, local dates, UTC calculations, and suspend/resume
  all need deterministic clocks.
- Long localized strings and fallback fonts are layout inputs, not polish.

### 5.6 Network proof lessons

- Containment and absence of attempted egress are separate claims.
- A network test must include liveness so a dead process cannot pass.
- Negative controls must prove the sink and syscall detector notice a deliberate
  request.
- A widget must preserve last useful data while visibly marking it stale.
- Default network configuration must never silently request a location that the
  user did not choose.

## 6. Marketing and media retrospective

### 6.1 Initial failures

The early video material did not meet the requested product-film standard:

- it looked like a slideshow rather than a behaving product;
- the simulated Edge had an incorrect foot or stand;
- Hub and Manager orientations did not always match;
- the opening bezel and camera movement visibly shook;
- the zoom-out to the desktop monitor stuttered;
- rotation was too slow and did not feel physical;
- captions changed harshly and sometimes appeared before the relevant screen;
- a Manager preview showed an empty fourth slot while the Hub showed three
  full-width widgets;
- themes, accents, screen creation, widget addition, layout changes, and
  settings were not demonstrated deeply enough;
- the first stills and film did not clearly separate editorial framing from
  real application output.

### 6.2 Final approach that worked

- Record synchronized real Hub and Manager behavior.
- Use isolated Xvfb environments when physical placement is not part of the
  claim.
- Drive real Manager input and the real local control socket.
- Put captured application pixels inside a clean, front-facing rounded bezel.
- Keep the device frame free of a fake foot.
- Animate camera and rotation editorially while keeping every screen pixel real.
- Match Hub and Manager orientation in every side-by-side frame.
- Supersample spatial motion at 7680x4320 and downsample to 1080p.
- Use one continuous camera path rather than separately rounded coordinates.
- Crossfade headlines and time them after the associated screen is visible.
- Verify continuity with objective velocity and acceleration measurements.
- Generate original music locally with no external samples or recordings.
- Create a separate Manager theme and accent showcase.
- Publish captions, hashes, reproduction scripts, and an explicit statement of
  what is live versus editorial.

### 6.3 Marketing lessons

- "Apple-esque" means controlled motion, continuity, restraint, typography,
  spatial confidence, and product truth. It does not mean adding generic glossy
  effects.
- Marketing must use the actual product state. Mismatched previews destroy
  trust faster than an imperfect but honest capture.
- Film continuity deserves a test plan just like software behavior.
- Legal safety is part of production: use an independent product frame, avoid
  third-party logos where unnecessary, state non-affiliation, and choose a
  repository name that does not imply ownership of another company's mark.
- User style rules are product requirements. The project removed em dashes from
  release-facing copy because the owner explicitly rejected them.

## 7. Agent collaboration retrospective

### 7.1 Attribution limits

Repository attribution is incomplete:

- all 546 recorded commits are authored by Simon or a variant of that identity;
- commit trailers record 317 Claude co-author entries: 153 for Claude Opus 4.8
  with 1M context, 113 for Claude Fable 5, 50 for Claude Opus 4.8, and one for
  Claude Sonnet 5;
- Codex work is mostly not identified by a standardized co-author trailer;
- no repository evidence attributes a specific commit or finding to Kimi;
- some work was performed by named task agents, reviewers, or "rubber duck"
  roles without durable provider/model metadata.

It would be inaccurate to assign unrecorded work to Claude, Codex, Kimi, or any
other model after the fact. The lessons below therefore describe observed agent
workflows rather than inventing a model leaderboard.

### 7.2 What worked well with agents

#### Bounded ownership

The multi-agent waves worked best when each agent owned a narrow file or
subsystem set:

- Rust core;
- C++ tests;
- QML orchestration;
- shared QML primitives;
- network widgets;
- coverage audit;
- integration.

Shared files such as `CMakeLists.txt`, CI workflows, and application bootstrap
needed a single owner. Git worktrees and frequent integration reduced
accidental overwrites.

#### Independent assurance

"Outstander" and rubber-duck roles were valuable when they:

- challenged whether a test asserted behavior or only executed code;
- explained a fix back in plain language;
- tried deliberate sabotage;
- reviewed the rendered result rather than the property model;
- checked another agent's claim from a clean environment.

This process found:

- tests that never ran;
- guards that matched no subjects;
- a property assertion that did not prove visible output;
- a test of an old `qrc` binary;
- a reduce-motion comment that was wrong;
- a second writer that could lose edits;
- generated code and package output accidentally entering source control;
- subtle date, font, layout, and process-lifecycle defects.

#### Sequential widget slices

The owner required one widget at a time, with one focused passing test before
starting the next. That constraint worked well because:

- each completion claim had a local proof;
- regressions were easier to attribute;
- partial work did not spread across 30 widgets;
- the final ledger clearly records the delivered behavior of each widget.

#### Persistent memory and handoff documents

The version-controlled Claude memory mirror, session handoff, backlog, audit
reports, and release ledger made it possible to resume a long project without
starting from zero. The best memory entries were:

- architecture facts;
- user decisions;
- exact test commands;
- known footguns;
- live versus historical status;
- paths to durable evidence.

#### Adversarial stranger walkthrough

An agent acting as a new user on the real machine found issues that code-centric
agents missed:

- autostart escaped the isolated XDG directory;
- widget config collapsed in landscape;
- preset library was wizard-only;
- software-rendered icons disappeared;
- Manager rename could lose typed text;
- display and diagnostics empty states were unclear;
- edit and swipe affordances were not obvious.

The walkthrough worked because it started from user tasks and only annotated
likely code causes after observing the product.

### 7.3 What did not work well with agents

#### Excessive breadth and repeated full suites

Agents repeatedly ran large suites when one focused failure was known. This:

- delayed release;
- consumed GitHub Actions minutes;
- consumed large token budgets;
- made the user wait without new information;
- increased the chance of unrelated flaky failures;
- reduced trust in the automation.

Correct approach:

1. reproduce the one failing case;
2. run its smallest owning test;
3. fix and rerun that case;
4. run the affected subsystem;
5. run the full suite once at the integration or release milestone.

#### Failure to react quickly to changed owner priorities

The user explicitly stopped caring about soak testing and asked to avoid long
runs. Agents continued to carry old gates and long-running behavior longer than
necessary. Owner waivers must immediately change execution, reporting, and
release plans. They do not turn a skipped test into a pass, but they do stop the
engineering team from repeatedly trying to run it.

#### Dirty shared worktree

A major audit ran on a dirty tree. Its output could not be attributed to one
commit. Multiple agents touching one working directory also created:

- uncertain ownership;
- evidence contamination;
- merge conflict risk;
- untracked files missed by checks;
- difficulty deciding which changes were intended.

Correct approach:

- one clean base SHA;
- one worktree per concurrent writer;
- explicit owned files;
- no formal evidence until integration is committed and clean;
- archive evidence under the exact full SHA.

#### Reports trusted before negative controls

Some agent reports confidently described guards that could not fail. A claim
such as "this test protects the URL" must include:

- the violation introduced;
- the expected red result;
- the actual red result;
- restoration;
- the green result.

Without that sequence, the reviewer must treat the claim as unproven.

#### Role simulation treated too literally

The planning phase used at least 15 roles such as product owner, tester,
accessibility specialist, marketer, lawyer, and sector user. This produced a
useful breadth of questions, but simulated roles are not 15 real people.

What role simulation can provide:

- structured review lenses;
- missing-question discovery;
- adversarial scenarios;
- consistent checklists.

What it cannot provide:

- legal advice;
- medical certification;
- real accessibility certification;
- real user research;
- professional sector sign-off;
- representative preference data.

Future plans must label simulated expert review as heuristic analysis and name
the real human validation still required.

#### External memory was not portable enough

Some approved plans and live Claude memory existed under `~/.claude/...`.
Repository mirrors helped, but live state could drift from the committed mirror.

Correct approach:

- keep project truth in the repository;
- treat provider-specific memory as a cache;
- sync important decisions immediately;
- include status dates and exact SHAs;
- delete or mark stale handoffs after they are superseded.

#### Weak model attribution

Inconsistent co-author trailer casing, model names, and missing provider data
make retrospective comparison impossible. There is no reliable way to answer
"Was Kimi better at X than Claude?" from this repository.

Future agent attribution should record:

- provider;
- model;
- session/task identifier;
- role;
- owned files;
- reviewer;
- commit(s);
- tests and negative controls;
- whether the output was accepted, revised, or rejected.

#### Hardware resource contention

Several agents and the owner used the same compositor and displays. This caused
focus interference and contaminated captures. Hardware tests need a lock and a
visible lease. No other agent should open product windows, inject input, change
orientation, or capture the desktop while the lease is held.

#### User-facing commands ignored the user's shell

A Bash block containing `set -euo pipefail` was given to a Fish user. It failed
before doing useful work.

Correct approach:

- detect or ask for the user's shell;
- prefer one repository script such as `./scripts/update-local.sh`;
- provide Fish syntax when the user is in Fish;
- keep strict Bash mode inside Bash scripts, not pasted into Fish;
- verify the exact command locally before handing it over.

#### Too much manual work delegated back to the owner

The manual touch audit asked the owner to perform an action, then failed to
capture the first screenshot with Spectacle. The owner had already said physical
input worked and did not understand what further work was expected.

Correct approach:

- preflight capture and storage before asking for the first action;
- explain the exact purpose and number of steps;
- automate everything that does not require human observation;
- request one concise human confirmation only for the irreducibly physical part;
- if the owner waives it, record `not tested` and continue.

#### Hidden signing prompt

The GPG tag operation opened pinentry outside the visible desktop context and
timed out repeatedly.

Correct approach:

- run a signing-key preflight before the release window;
- update the GPG agent's desktop and TTY context;
- force a visible platform when required;
- focus the pinentry window;
- never ask the user to reveal the passphrase;
- separate secret-dependent signing from the rest of the automated release so
  one unlock completes every required signature.

#### Post-publication metadata was checked too late

The release was already public when the published-stage contract found stale
`ROADMAP.md` and `SECURITY.md` state. It was fixed immediately on `master`, but
the tagged source retains the earlier text.

Correct approach:

- prepare the published documentation state before tagging;
- run the published-stage contract against the staged release tree;
- only then sign and publish;
- use a two-phase release driver that can validate future public state without
  falsely claiming the release is already public.

#### Ad hoc shell test masked a failure

During final public verification, an ad hoc zsync command did not enable strict
shell mode. The legacy client failed, later hash and compare commands also
failed, and an unconditional final echo printed PASS. The transcript was
immediately reclassified as failed, and the supported official updater was then
tested successfully.

Correct approach:

- every multi-command verification uses `set -euo pipefail` in Bash;
- no unconditional PASS message;
- assert expected files and exit codes before reporting;
- capture the exit status of expected nonzero commands explicitly;
- prefer maintained test scripts over one-off shell blocks;
- make the release report include failed attempts as well as the eventual pass.

## 8. Process and safety practices that worked

- Recovery snapshots before broad edits or hardware activity.
- Binary-safe patches, refs, untracked-source inventory, config copy, display
  inventory, and hashes in each checkpoint.
- Preserving unrelated user changes in dirty trees.
- Exact PID and private runtime directories instead of broad `pkill` patterns.
- Graceful SIGTERM so the Hub can flush state.
- Config checksum before and after hardware campaigns.
- Display restoration in `finally`.
- Input-device restoration in traps.
- Refuse-on-uncertainty input behavior.
- Private Xvfb captures for Manager theme work.
- Cropping captures to the intended application or display.
- Moving rejected user-visible media to Trash instead of permanently deleting
  it.
- Commit-keyed evidence outside `/tmp`.
- Signed evidence manifests after producers close their files.
- Fresh public download verification after release publication.

## 9. Process and safety practices to improve

- Formal testing must never start from a dirty tree.
- Evidence should not spend any stage only in `/tmp`.
- Every artifact producer must close before hashing.
- Untracked Markdown and source-like files must be included in local checks.
- One agent should own release state and publication metadata.
- One agent should own shared build and CI files.
- Hardware and desktop interaction need an exclusive lease.
- Signing, package credentials, license keys, and privileged install prompts
  need an early preflight.
- System-wide package installation should be the last owner action, not a
  surprise after a long build.
- The user's current config and process state must be captured before upgrade
  and restored according to explicit policy.

## 10. Recommended agent operating model for the next project

### 10.1 Task contract for every agent

Every delegated task should state:

```text
Goal:
Non-goals:
Exact base SHA:
Owned files:
Shared files that must not be edited:
User-visible acceptance criteria:
Smallest focused test:
Required negative control:
Expected artifacts:
Time and compute budget:
Stop conditions:
Required report fields:
```

### 10.2 Required agent report

Every agent should return:

1. exact starting and ending SHA;
2. clean or dirty tree status;
3. changed files with one-line purpose;
4. commands executed;
5. actual pass/fail/skip counts;
6. the deliberate violation used to prove the guard turns red;
7. evidence path and hashes;
8. what was not tested;
9. remaining risks;
10. suggested next action;
11. provider/model/task attribution.

### 10.3 Integration policy

- Builders use isolated worktrees.
- Shared files have one owner.
- Integrate small commits frequently.
- Rebase or merge onto one clean integration SHA.
- Run focused tests after each slice.
- Run subsystem tests after each integration wave.
- Run the complete local suite once per release candidate.
- Run expensive hosted compositor and packaging work only on the exact candidate.
- Cancel duplicate hosted work when exact local evidence is already authoritative
  and the hosted duplicate exceeds its agreed budget.

### 10.4 Test budget policy

Recommended default:

| Stage | Test scope |
|---|---|
| Reproduction | One failing test or one minimal scenario |
| Local fix loop | The failing test only |
| Slice completion | Focused file or subsystem |
| Integration wave | Affected layers |
| Release candidate | Full local suite once |
| Hosted candidate | Only gates that need hosted, distro, or clean-container infrastructure |
| Public release | Fresh download, signature, checksum, install/update round trip |

Every long job needs:

- a wall-clock timeout;
- a process-tree resource limit where appropriate;
- progress output;
- an explicit cancel rule;
- a statement of what new evidence it adds.

### 10.5 Hardware lease

The lease record should include:

- owner;
- start and maximum end time;
- target outputs;
- target input devices;
- target process PIDs;
- baseline display configuration;
- baseline config hash;
- allowed disruptive actions;
- restore command;
- live abort inputs;
- final restoration proof.

No other agent may interact with the compositor until the lease closes.

### 10.6 Release state machine

Use explicit states:

1. development;
2. clean candidate;
3. signed RC;
4. public RC validation;
5. stable metadata prepared;
6. signed stable tag;
7. stable artifacts built;
8. public stable release;
9. public bytes verified;
10. immutable archive complete.

Each transition has one command and one machine-readable receipt. Owner waivers
are separate signed or recorded inputs, not fake green checks.

### 10.7 Documentation policy

- One current backlog owns open work.
- One release ledger owns release state.
- Historical plans are labeled historical.
- Provider-specific memory is never the sole source of truth.
- Every current claim names its evidence location.
- Every compatibility claim names the tested platform.
- Every media claim distinguishes real application output from editorial
  framing.
- Run the published metadata contract before the tag, not after users can
  download it.

### 10.8 User communication policy

- Lead with the current outcome.
- State what is running and why.
- Update at least once per minute during long work.
- Quote the exact remaining blocker and estimated next step.
- Stop immediately when the user changes priority.
- Do not restart a waived test.
- Do not give Bash syntax to a Fish user.
- Prefer a repository script over a long pasted command.
- Ask for secret input only through the user's local secure prompt.
- Never call a skipped action a pass.
- Do not use em dashes when the owner has prohibited them.

## 13. Final reusable conclusions

1. Start with a clean SHA and never lose it.
2. Give every concurrent agent bounded ownership.
3. Treat shared files and hardware as exclusive resources.
4. Make every gate prove it has subjects.
5. Make every new guard prove it can fail.
6. Test rendered behavior, not only properties.
7. Use the smallest failing test during implementation.
8. Run broad suites only at explicit integration milestones.
9. Separate automated evidence, human observation, owner waiver, and
   professional certification.
10. Build systemic design tokens before opening dozens of duplicate visual
    tickets.
11. Use actual widgets and actual geometry for previews.
12. Use real application behavior for marketing.
13. Keep media continuity and legal truth in the acceptance criteria.
14. Package and update testing must use exact public bytes.
15. Verify the public download after publication.
16. Preflight signing, shell compatibility, capture tools, permissions, and
    privileged prompts before the final release window.
17. Put important memory in the repository.
18. Standardize agent attribution if model comparison matters.
19. Stop immediately when the owner changes priorities.
20. Honest uncertainty creates more trust than a green claim the evidence does
    not support.
